The Problem We're Solving

  • Product teams need AI agents that act, not just answer
  • Upgrades, diagnostics, remediation, compliance — multi-step workflows with real consequences
  • Customers are already using frontier models without guardrails
  • Every team is building their own agent harness — duplicated effort, inconsistent security
"If we don't provide native AI capabilities, customers will use uncontrolled frontier models."
— Dan Prince, June 2026

Without a framework

  • Each team builds sandbox, auth, retry, escalation from scratch
  • No consistent security model for AI writes
  • No approval gates — or inconsistent ones
  • No audit trail across products

With Cloud Agents

  • Define workflows in YAML, no framework code
  • Security, isolation, approval gates built in
  • Same workflow runs on K8s and Podman
  • Full observability + audit trail

Workflow Model

Declarative YAML — No Code Changes

# cve-patch-workflow.yaml apiVersion: v1 kind: AgentWorkflow metadata: name: cve-patch-workflow spec: steps: - name: scan-components type: agent prompt: | Scan the RHDH catalog for components affected by {{ input }} output_key: scan_result permissions: allowed_tools: - rhdh_list_components - rhdh_get_component - name: approve-patch type: human-approval risk_level: high message: | Review affected components: {{ steps.scan_result.output }} - name: apply-patches type: agent prompt: | Create PRs patching each affected component... condition: | steps.approval.output.approved

Key Concepts

  • Steps — agent (AI does work) or human-approval (human gates)
  • Conditions — steps run only when prior outputs satisfy rules
  • Interpolation — {{ steps.X.output.Y }} passes data between steps
  • Per-step tool filtering — each step gets only the MCP tools it needs
  • Risk levels — low = auto-approve, high = human review
  • Output schema — agents return structured Pydantic models

OpenStack Relevance

Your upgrade workflow maps directly: pre-flight check (read-only agent step) → admin approval (human gate) → execute upgrade (scoped agent step) → verify (agent step).

GitOps pattern: the "execute" step creates a Git commit/PR rather than running destructive ops directly.

Security & Governance

Defense in Depth for Agent Execution

Sandbox Isolation

  • Fresh container per step
  • Non-root, read-only rootfs
  • No privilege escalation
  • Hard timeout enforcement
  • CPU/memory resource limits
  • Network egress policy
    (DNS + LLM CIDRs only)

Credential Scoping

  • Per-step K8s Secrets mount
  • Per-step ServiceAccount
  • MCP secret allowlist
  • File-ref headers — secrets never in env vars
  • App-level TLS
    (ephemeral CA + per-sandbox certs)
  • Bearer auth runner ↔ sandbox

Governance

  • RBAC: who can trigger, approve, view, cancel
  • Risk-level driven approval gates
  • Per-step tool allow/deny lists
  • Structured audit trail
  • Advisory mode (dry-run)
  • Concurrency cap on pods

GitOps as the Write Pattern

For AI-driven write operations: agent drafts changes → Git commit / PR → human approval → controlled application (ArgoCD/Flux). This is the pattern that gets PM buy-in for agentic writes. The framework supports it natively via agent step + GitHub/GitLab MCP server + approval gate.

Tool Scoping

Per-Step Tool Filtering via MCP

One MCP server exposes many tools. Each workflow step declares which tools it can use — the framework enforces the boundary.

kubectl MCP server exposes: kubectl_get_pods kubectl_get_nodes kubectl_get_events kubectl_describe kubectl_apply ← write kubectl_delete ← write kubectl_scale ← write kubectl_exec ← dangerous Diagnose step: allowed_tools: [get_pods, get_nodes, get_events, describe] → read-only investigation Fix step (after approval): allowed_tools: [get_pods, apply, scale] denied_tools: [delete, exec] → controlled remediation

How This Maps to OpenStack

  • Upgrade agent: read-only tools for pre-flight checks
  • Health check agent: diagnostic tools only
  • Remediation agent: scoped write tools, gated by approval

Same MCP server, different tool sets per step. No need to build separate servers for read vs write.

Credential Isolation

Each step can mount a different credentials_secret and use a different service_account. The diagnose step gets a reader SA; the fix step gets a writer SA.

Per-user credential derivation (e.g. Keystone tokens) is a planned integration point.

Deployment

K8s and Podman — Same Workflow Model

Kubernetes (OCP) ├── Temporal Server (Deployment) ├── PostgreSQL (StatefulSet) ├── Workflow Runner (Deployment) ├── MCP Servers (Deployments) └── Sandbox steps (K8s Jobs, ephemeral) ├── NetworkPolicy (egress restrict) ├── ServiceAccount (per-step RBAC) └── securityContext (non-root, ro-fs) Podman (RHEL) ├── Temporal Server (container) ├── PostgreSQL (container) ├── Workflow Runner (container) ├── MCP Servers (containers) └── Sandbox steps (Podman containers) ├── Podman network (DNS isolation) ├── Host firewall (egress restrict) └── rootless Podman (no root needed)

Why This Matters for OpenStack

  • Air-gapped / sovereign cloud — same workflow runs disconnected from external services
  • On-prem RHEL — Podman deployment, no K8s dependency
  • OCP — full K8s native with RBAC, NetworkPolicy, ServiceAccounts
  • Model flexibility — ProviderConfig is provider-agnostic; works with local/offline LLMs

OpenShell Integration (Planned)

OpenShell Gateway adds Landlock + seccomp + L7 network policy on top of container isolation. One spawner, unified across K8s and Podman.

Agent HTTP contract stays identical — the security layer is transparent to the workflow.

The Hybrid Model — Agreed Architecture

Cloud Agents = server-side platform

  • Well-defined workflows (RCA, upgrades, compliance)
  • Central portal for triggering agentic workflows
  • Approval gates, audit trail, observability

Client agents (Goose/equivalent) = ad hoc

  • Interactive CLI troubleshooting
  • Local action execution with user-scoped creds
  • Tasks requiring direct cluster access

Cloud Agents is not trying to replace client-side agents. Both coexist.

Working Demo Scenarios

K8s Incident Response

Diagnose → Approve → Fix → Verify

Uses kubectl MCP server with real cluster access. Per-step tool filtering: read-only for diagnose, scoped writes for fix.

CVE Patch Workflow

Scan RHDH catalog → Approve → Create PRs → Verify

Uses RHDH catalog MCP server. GitOps pattern: agent creates PRs, human reviews.

Security Audit

Scan → Assess risk → Approve → Remediate

Multi-step with condition evaluation. Advisory mode for dry-run audits.

Escalation & Handoff

Agent fails → Package context → Human follow-up

Full transcript persistence. Context includes tool call history, LLM reasoning, prior attempts.

OpenStack Upgrade Workflow maps directly to these patterns: pre-flight health check (read-only agent) → admin reviews findings (approval gate) → execute upgrade steps (scoped agent, GitOps) → verify cluster health (read-only agent). All with per-step tool filtering and credential scoping.
